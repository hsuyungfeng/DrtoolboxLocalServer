<objective>
Consolidate SQLite and Chroma onto one chunking pass with a shared `chunk_id` (D-07), and make the real production write path — `RAGEngine.ingest_special_data()` / `ingest_general_data()`, called on every server restart by `HermesAgent._initial_ingest()` — write to both stores idempotently, so an unchanged corpus does not get re-chunked/re-embedded on every restart. This is Stage 3: it makes the RRF fusion built in Plan 10-02 actually correlate sparse and dense hits by identity instead of degenerating to rank-only fusion.

Purpose: Today `SimpleIndex.add_document()` (SQLite) and `DocumentIngestor.chunk_text()` (Chroma, used only via the separate `scripts/rebuild_rag.py`/`/api/v1/rag/ingest` paths) chunk the same source documents independently with different boundaries, and there is no `chunk_id` column in `rag_chunks` at all — so `HybridRetriever`'s content-hash correlation (Plan 10-02) can only match chunks that happen to be byte-identical, which is rare. Separately, `HermesAgent._initial_ingest()` unconditionally re-walks and re-ingests the entire document corpus on every server startup with no skip-if-unchanged check — naively wiring Chroma writes into that path would re-embed ~1,700+ documents on CPU every restart.
Output: A single chunker (`DocumentIngestor.chunk_text()`) feeding both SQLite `rag_chunks` (now with a `chunk_id` column) and Chroma, driven from `RAGEngine.ingest_special_data()`/`ingest_general_data()`, gated by a content-hash skip so unchanged documents cost nothing on restart.
</objective>
